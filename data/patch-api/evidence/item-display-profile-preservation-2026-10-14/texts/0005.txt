The staged four-route fixture is **not ready to claim four-route behavioral RED**. Three issues change that conclusion:

1. **C_Item test does not exercise item cooldown selection.** Current `c_item_get_item_cooldown` (`src/c_api/item_spell/c_item.rs:746-752`) ignores argument 1 and unconditionally returns `(0,0,true)`. Existing `parse_item_id_from_val` handles numeric IDs and `item:`/`|Hitem:` strings, but the actual `GetItemIDForItemInfo` helper at lines 654-660 is a separate selector; `GetItemCooldown` does not call it. Therefore numeric-vs-hyperlink checks on `GetItemIDForItemInfo` are controls only. Against the staged expected `(11,31,true)`, both cooldown assertions fail on the current constant stub, but that demonstrates only constant output, not parsing/selection. To establish the intended ItemInfo selector boundary, assert the actual cooldown route with numeric and concrete hyperlink inputs after a producer change, or add a direct helper-level contract only if that is the chosen scoped requirement. Do not label current test RED as proof of hyperlink resolution.
2. **C_Container test calls a two-argument route with one argument.** Registration aliases both `GetItemCooldown` and `GetContainerItemCooldown` to `c_container_get_item_cooldown` (`c_container.rs:78-79`), whose present implementation parses only arg1 and returns constants (`231-236`). The fixture's three `C_Container.GetItemCooldown(itemID)` calls are structurally covered as the currently registered call shape, but cannot establish the future item's map selection. Its route's actual input ABI/signature is not proven by the staged report; verify the governing declaration before fixing the test. The bag-slot route accepts `(bag,slot)` and `GetContainerItemID` reads the bag map (`239-246`), so that route is a real distinct selector and is the strongest current behavioral boundary.
3. **Legacy missing-slot expectation is unproved and likely inconsistent with backing defaults.** The fixture removes slot 15 from `inventory_item_cooldowns`, but `GetInventoryItemCooldown` obtains three values with its own semantics; staged report says the existing missing policy is `(0,0,1)`, which must be checked against lines 85-101. Treat its exact enable expectation as source-specific, not interchangeable with C_Item/container policies.

Also, the staged fixture seeds bags `(0,8)` and `(0,13)` but does not prove those slots are absent from `SimState::default()`; the private report should not claim only explicitly inserted records are present without checking default backpack population. Existing `EmptyStateCollections::new()` seeds `default_backpack_items()` (state.rs:776-780). The fixture must overwrite/remove those keys deterministically before asserting occupant controls.
