## Literal producer mapping

`inline_scroll_argument_locals(handler_name)` supplies local declaration text only for inline XML script bodies in `build_handler_expr`:

| Handler name | Generated locals | Values sourced from |
|---|---|---|
| `OnHorizontalScroll` | `local offset = ...;` | first vararg after `self` |
| `OnVerticalScroll` | `local offset = ...;` | first vararg after `self` |
| `OnScrollRangeChanged` | `local xrange, yrange = ...;` | first and second varargs after `self` |
| `OnMouseWheel` | `local delta = ...;` | first vararg after `self` |
| other names | empty | no extra aliases |

The handler signature still comes from `handler_params`: these handlers take `self, ...`. The emitted function body puts the local declarations before the original trimmed XML body. The declarations read `...` without replacing/removing it, so body `...` remains available. The locals shadow globals of the same names only inside these inline function closures.

Function-backed scripts return the named function unchanged; method-backed scripts use `__wow_bind_xml_method(...)`. Neither takes the inline-body alias path. Binding selection and `SetScript`/intrinsic-binding emission happen outside `build_handler_expr`; the producer change does not alter those paths. For append/prepend inheritance, the composed wrapper forwards `self, ...` to both handlers; the generated inline closure then binds its own locals.

Ordinary scripts route through `generate_scripts_code` → target generator → lifecycle/input handler lists → append/build logic. Runtime templates use the template installation/generation routes and the same shared handler-expression producer. Inspection supports shared producer coverage, not a claim that every possible runtime installation scenario was executed.
