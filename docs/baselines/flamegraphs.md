# Per-profile flamegraphs (Phase 9.4)

Flamegraphs visualize where wall-clock time goes during wow-sim
startup. Each profile produces a separate SVG so the per-profile
hot spots can be compared side-by-side.

Generated by `scripts/bench-flamegraph.sh`. Output lands in
`target/flamegraphs/<profile>.svg` (gitignored — flamegraphs are large
SVGs and stale quickly; regenerate from a current commit when needed).

## Quick start

```bash
# Lower perf paranoid level once per boot (no sudo needed for cargo run)
sudo sysctl kernel.perf_event_paranoid=1

# All five profiles, release build, lua-errors as the workload
./scripts/bench-flamegraph.sh

# Single profile
./scripts/bench-flamegraph.sh wrath

# Debug build (cheaper, much noisier)
./scripts/bench-flamegraph.sh --debug

# Different workload
./scripts/bench-flamegraph.sh --command dump-tree

# Open in browser
xdg-open target/flamegraphs/retail.svg
```

## What's measured

`cargo flamegraph` wraps `cargo run` in `perf record -F 997` (sampling at
~1 kHz), then converts the perf.data trace through inferno-flamegraph
into an interactive SVG. Each row in the SVG is a stack frame; row
width is proportional to time spent in that frame plus its callees.

Workload defaults to `wow-sim lua-errors` (covers the full startup
path: rilua init → Blizzard UI load → addon load → startup events →
JSON emit → exit). Override with `--command dump-tree` for a workload
that includes the frame-tree dump pass, or `--command screenshot` to
profile the GPU-render path.

## Interpreting the output

Common hot paths to expect:

- **`rilua::vm::*` / Lua interpreter** — usually the largest chunk
  during addon loading. Function-call dispatch, table-lookup, and
  closure execution dominate.
- **`loader::xml::*` / quick-xml** — XML parse + frame instantiation.
  Larger on profiles with more vendor frames (mists 17K, wrath 15K).
- **`asset_resolver::*` / CASC** — texture resolution from the WoW
  install. Cold cache dominates on first run; subsequent runs hit the
  on-disk extract cache.
- **`cosmic_text::*` / glyph shaping** — only relevant when a workload
  exercises text rendering (screenshot, GUI). Negligible under
  `lua-errors`.

If a profile shows a tall narrow tower in `lua_api::globals::*`, that
tells you a global function is being hammered during startup. If it
shows a wide flat base in `loader::xml::process_*`, the XML pass is
dominated by some specific tag handler.

## Requirements

- `cargo install flamegraph` (cargo-flamegraph plugin)
- `perf` from `linux-tools` / equivalent
- `kernel.perf_event_paranoid` ≤ 1, OR run with sudo. Persistent on
  Arch:
  ```
  echo 'kernel.perf_event_paranoid = 1' | \
      sudo tee /etc/sysctl.d/99-perf.conf
  ```
- Default to release builds: debug-profile call stacks contain so much
  optimization-disabled noise that real hot spots get drowned out.

## Known caveat: release-build symbol resolution

The Cargo profile sets `debug = "line-tables-only"`, which gives line
numbers but limited call frames. Release flamegraphs therefore show
mostly kernel symbols (`__alloc_frozen_pages_noprof`,
`asm_exc_page_fault`, etc.) and few Rust user-space frames. For a
finer-grained capture, temporarily flip the profile in Cargo.toml:

```toml
[profile.release]
debug = "full"        # was "line-tables-only"
```

then rebuild from clean. Don't commit that change — it doubles binary
size and slows builds. Use it only when the flamegraph isn't telling
you what you need.

For most regression hunts, the wall-clock + memory benches give a clear
enough signal without needing user-space stack resolution.

## Tracking regressions

Flamegraphs are visual; they're not auto-diffable. The workflow is:

1. Generate a flamegraph from `master`.
2. Generate a flamegraph from the proposed change.
3. Open both side-by-side; if a previously-thin column got wider, that's
   a hot-path regression.

For numeric regression tracking, use the wall-clock bench instead
(`scripts/bench-startup.sh` / `docs/baselines/startup-bench.tsv`). The
flamegraph answers *why* a regression happened; the bench answers
*whether* one happened.

## What's deliberately NOT included

- **CI integration.** Flamegraphs need `perf`, kernel privileges, and
  produce large SVGs — none of which is friendly to a default
  GitHub-hosted runner. Generate locally on the dev box; commit
  observations to a wiki investigation rather than the SVG.
- **GUI mode.** `cargo flamegraph` running an interactive GUI app
  blocks until the user closes the window. Profile `lua-errors` or
  `dump-tree` for headless captures.
- **Long-running workloads.** Default workload finishes in ~15s
  (release). For longer captures, pass `--command run-tests <addon>`
  or use perf directly.
